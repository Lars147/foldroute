# FoldRoute Webplaner

[Projektübersicht](../README.md) · [Routingdetails und Plattformgrenzen](../documentation/routing.md)

Browserbasierte Routenplanung für Faltrad und ÖPNV. Vite/TypeScript, Leaflet und direkte Transitous-Anfragen; kein eigener Server, keine Konten, keine Analyse-Tools. Gültige Routing-Einstellungen werden in `localStorage` gespeichert. Die standardmäßig eingeschaltete Strecken-Speicherung hält bis zu 20 unterschiedliche geplante Strecken einschließlich Start, Ziel, Zwischenzielen, Etappen, Geometrie, Einstellungen und Abfragezeit in IndexedDB. Ausschalten löscht diesen Verlauf; Favoriten, bis zu 20 zuletzt ausgewählte Orte und Einstellungen bleiben lokal erhalten. „Alle lokalen Daten löschen“ entfernt auch diese Daten. Abgesehen von ausdrücklich geteilten, noch nicht übernommenen Zielen werden keine eingegebenen Suchtexte und keine GPS-Spuren gespeichert. Ortssuchen und Planungsangaben einschließlich gewählter Zwischenziele gehen an Transitous; Kartenabrufe einschließlich Kartenschriften an OpenFreeMap (Kartendaten von OpenStreetMap).

Die Einstellungen zeigen Radtempo, Radzeit und Faltzeit direkt. Verkehrsmittel, weitere Routenoptionen, Datenverwaltung und Hilfe lassen sich unabhängig aufklappen. „Fertig“ oben rechts führt zurück; gültige Änderungen gelten sofort, eine bestehende Route wird erst beim Verlassen einmal neu berechnet. Persönliche Vorgaben gelten für jede neue Berechnung, auch aus Links, Verlauf und Navigation. Das Öffnen einer alten Reise verändert sie nicht.

## Darstellung

Unter **Einstellungen → App & Speicher → Darstellung** stehen **System**, **Hell** und **Dunkel** zur Wahl. Standard ist **System**, das auch während der Nutzung auf Änderungen der Geräteinstellung reagiert. Die Auswahl gilt sofort für Oberfläche, Routen- und Navigationspanels und wird separat unter `foldroute.appearance` in `localStorage` gespeichert. Sie verändert keine Routen und löst keine Neuberechnung aus. Ohne Speicherzugriff gilt sie für die laufende Sitzung. „Alle lokalen Daten löschen“ setzt sie auf **System**; „Routeneinstellungen zurücksetzen“ erhält sie. Die Bedienflächen des Planers unterstützen Hell und Dunkel. Über das Ebenen-Symbol direkt auf der Karte stehen **Positron**, **Straßenkarte** und **Dunkel** zur Wahl, auch während der Navigation. Standard ist Positron. Die Wahl gilt unabhängig vom App-Modus und wird separat unter `foldroute.mapStyle` gespeichert und zwischen Tabs synchronisiert. Kartenwechsel erhalten Route und Ausschnitt. Routen, Standort und Kartenmarker passen sich dem gewählten Kartenstil an. „Alle lokalen Daten löschen“ stellt Positron wieder her; ohne Speicherzugriff gilt die Auswahl für die Sitzung. Die Landingpage bleibt immer hell und liest oder verändert die Darstellungswahl nicht. Die öffentliche Beispielroute liest ausschließlich Darstellungswahl und Kartenstil, keine persönlichen Routing-Einstellungen oder gespeicherten Fahrten.

## Entwickeln und bauen

Voraussetzung: Node.js 22.12+ und npm.

```sh
cd web
npm ci
npm run dev
npm test
npm run build
```

Der Build ersetzt ausschließlich `docs/plan/`. Landingpage und deren Assets bleiben erhalten. GitHub Pages kann weiterhin das Verzeichnis `docs/` ausliefern; der Planer liegt unter `plan/`. Relative Bundle-URLs funktionieren auch unter einem Repository-Unterpfad. Zum lokalen Testen die Seite über HTTP öffnen, nicht über `file://`. `npm run preview` liefert den fertigen Build aus.

## PWA-Start

Beim Kaltstart der installierten PWA bleibt das Faltradlogo sichtbar, bis Bedienung und lokale Wiederherstellung bereit sind. Die Radhälften bewegen sich einmal kurz um das gelbe Gelenk und kehren in die Ausgangslage zurück. Die Bewegung verzögert den App-Start nicht und entfällt bei „Bewegung reduzieren“. GPS, Routenabfragen und Kartenkacheln verzögern diesen Übergang nicht. Die Ladeoberfläche übernimmt die gespeicherte Darstellung, sonst die Systemeinstellung. Fehlgeschlagene Starts bieten „Neu laden“. Normale Browseraufrufe erhalten keinen zusätzlichen Splashscreen.

Die Animation beginnt, sobald die PWA rendert. Die kurze Systemanzeige davor bleibt auf iPhone/iPad dem Betriebssystem überlassen; gerätespezifische PNG-Startbilder werden nicht ausgeliefert. Android erzeugt seinen System-Splash weiterhin aus dem Manifest mit hellem Hintergrund und vorhandenem App-Icon. Der tatsächliche Systemstart muss auf einem Gerät mit installierter PWA geprüft werden.

`public/foldroute-mark.svg` ist die einzige Logoquelle. Vite bettet sie in Entwicklung und Produktionsbuild direkt ins HTML ein; die Striche übernehmen dabei die aktuelle Textfarbe. Zusammen mit den kritischen Startstilen ist das Logo bereits vor dem JavaScript-Bundle verfügbar und über das gespeicherte HTML auch offline nutzbar. Ein separater Bildexport entfällt.

Nur im Dev-Modus zeigt `/splash-preview/` dieselbe Oberfläche mit Hell/Dunkel, Fortsetzen und Wiederholen. Die Vorschau pausiert ausdrücklich, lädt keine persönlichen Reisen und verändert keine Einstellungen. Der Produktionsbuild enthält diese Vorschauseite nicht.

## Gesamte Website lokal ansehen

Im Dev-Modus (`npm run dev`) liegen Landingpage und Planer auf demselben Server: [Landingpage](http://127.0.0.1:4173/landing/) und [Planer](http://127.0.0.1:4173/). Änderungen werden automatisch aktualisiert. Die Landingpage bleibt hell; die Darstellungswahl in den App-Einstellungen gilt für den Planer und die interaktive Beispielroute.

Die Landingpage liegt in `docs/index.html` und benötigt selbst keinen Build. Logo, HTML, CSS, JavaScript und Vorschaubild liegen lokal. Die Karten sind Illustrationen; die Webplaner-Vorschau zeigt die echte Oberfläche mit Beispieldaten. Für echte Planung führt der Link zu `plan/`.

„Beispiel öffnen“ führt zu `plan/?example=bike-transfer`. Dieser getrennte Einstieg lädt eine feste, interaktive Verbindung mit S8, Radfahrt zwischen Unterföhring und Freimann und U6 nach Fröttmaning. Karte und Etappendetails verwenden dieselben Ansichten wie der normale Planer. Die Beispielansicht zeigt ausschließlich Dauern und fragt weder Routing noch Standort ab. Sie übernimmt nur Darstellungswahl und Kartenstil und liest oder verändert keine Routing-Einstellungen, Strecken oder Navigationsstände. „Eigene Route planen“ öffnet den normalen Planer ohne vorbelegte Route.

Die vollständige Aufzeichnung liegt in `src/data/bike-transfer.json`: am 16.10.2026 über Transitous mit den damaligen Standardeinstellungen für Abfahrt am 19.10.2026 um 08:00 Uhr in München geprüft. Die ausgewählte Verbindung dauert 57 Minuten; die Radetappe zwischen Unterföhring und Freimann ist rund 3,8 km lang und dauert 17 Minuten. Das JSON enthält Herkunft, Abfrage, Einstellungen, alle Etappen und ihre Geometrien; flüchtige Echtzeit- und Fahrtkennungen wurden entfernt. Eine Aktualisierung erfolgt bewusst durch Ersetzen dieser Aufzeichnung nach erneuter Prüfung. Die Beispieladresse führt keine neue Suche aus und verspricht keine aktuelle oder schnellste Verbindung. Die Straßenkarte nutzt wie sonst OpenFreeMap mit OpenStreetMap-Daten; ohne Kacheln bleiben Verlauf und Etappen verfügbar.

Aus dem Repository-Hauptverzeichnis den Webplaner bauen und anschließend die Website ausliefern:

```sh
cd web
npm ci
npm run build
cd ..
python3 -m http.server 4174 --bind 127.0.0.1 --directory docs
```

- Landingpage: [http://127.0.0.1:4174/](http://127.0.0.1:4174/)
- Gebauter Webplaner: [http://127.0.0.1:4174/plan/](http://127.0.0.1:4174/plan/)

Bei reinem Landingpage-Text- oder CSS-Ändern genügt Neuladen. Änderungen am Webquellcode erfordern für diese Vorschau einen neuen Build. Der Entwicklungsserver auf Port 4173 liefert dagegen direkt den Planer unter `/` mit automatischer Aktualisierung.

Die Landingpage zeigt unterhalb des Vergleichs einen Screenshot der echten mobilen Verbindungsliste mit Beispieldaten. Zum Erneuern zuerst den Web-Entwicklungsserver starten und in einem zweiten Terminal unter `web/` ausführen:

```sh
node scripts/capture-landing-preview.mjs
```

Das Skript benötigt Playwright Chromium und ersetzt `docs/assets/webplaner-vorschau.png`. Es verwendet die vorhandenen Routing-Testdaten, eine feste Uhrzeit und einen leeren Browserkontext in Hell bei 390 × 844 px und doppelter Pixeldichte. Routinganfragen werden abgefangen, Kartenabrufe blockiert. Eine andere lokale Planer-Adresse kann als Argument übergeben werden.

## Tests

Die folgenden Befehle werden in `web/` ausgeführt. Die Browsertests benötigen standardmäßig die Ports 4173 und 4174 exklusiv. Mit `FOLDROUTE_TEST_PORT=4283 npm run test:browser` nutzen sie stattdessen 4283 und 4284, ohne laufende Vorschauen zu beenden. Ihr Testserver liefert das Repository-Hauptverzeichnis aus, weshalb der interne Testpfad `/docs/plan/` von der obigen Website-Vorschau abweicht.

```sh
npm run test:parity
npx playwright install chromium webkit
npm run build
npm run test:browser
```

Die Browsertests benötigen zusätzlich Python 3 für den statischen Testserver. Service-Worker-Tests laufen auf dem fertigen Build unter einem Unterpfad. Der Paritätstest benötigt macOS und Swift. Er kompiliert die unveränderten nativen Routingdateien aus `../ios/` und führt sie mit `URLProtocol`-Testantworten aus, ohne Netzwerkzugriff. `tests/fixtures/swift-parity.json` enthält dieselben normalisierten Transitous-Antworten und native Referenzergebnisse. Vitest vergleicht daraus Abfahrten, Ankünfte, Etappen, Faltzeiten und Auswahl. Nach bewussten nativen Änderungen: `sh scripts/parity.sh --update`; anschließend die Referenzänderungen prüfen. Der Harness ersetzt ausschließlich den für Routing irrelevanten Typ `NavigationProgress`.

Zusätzliche Tests prüfen Anfrageparameter, Ausschlüsse, Geometrie, Zeitvorteil, Vorwärts-/Rückwärts-Verknüpfung, Teilergebnisse, Abbruch und Rate-Limits. Browsertests verwenden abgefangene API-Anfragen und keine echten Routingdienste. Screenshots entstehen für 320, 390, 768 und 1479 Pixel Breite. Das sind gezielte Paritätsfälle, kein Beweis identischer Ergebnisse für alle denkbaren Netze und Datenfehler. Der Vergleich prüft gemeinsame Standardwerte von jeweils 180 Sekunden und zusätzlich Abfahrts-/Ankunftsfälle mit 60, 150 und 360 Sekunden je Vorgang. Weitere Tests prüfen Favoriten, Migrationen, Auswahl während der Nachsuche und Einstellungen. Die browserseitige Distanzprüfung verwendet Haversine, die App CoreLocation; Grenzfälle direkt an Abstandstoleranzen können abweichen.

## Routing und Grenzen

- Direkte Radroute sowie vier Kombinationen aus Rad-/Fuß-Zubringer und -Abbringer.
- Konfigurierbare Geschwindigkeit, Zugangszeiten, Falt-/Entfaltzeiten, Verkehrsmittel und zusätzliche Radverbindungen zwischen Linien.
- Progressive Ergebnisse; bis zu drei reguläre Alternativen plus optionaler Fahrradvergleich. Eine ausdrücklich ausgewählte Reise oder das bewusste Öffnen ihrer Details hält die Auswahl beim Nachladen; sonst folgt die automatische Auswahl besseren Ergebnissen.
- Maximal zwei gleichzeitige Routinganfragen. Zusätzliche Rad-Umstiege: höchstens vier Anfragen je Tiefe, maximal drei Tiefen und insgesamt 15 Sekunden Suchbudget. Geometriefehler werden einmal erneut abgefragt; HTTP-Fehler werden nicht automatisch wiederholt.
- „Falten / Entfalten“ verwendet wie iOS eine gemeinsame Dauer: Standard 180 Sekunden je Vorgang, einstellbar von 60 bis 600 Sekunden in 30-Sekunden-Schritten. Bisherige getrennte Einstellungen werden beim Laden auf den größeren Wert zusammengeführt.
- HTTP 429 und lesbare `Retry-After`-Angaben bei 429/503 stoppen weitere Planung. Eine laufende zweite Anfrage kann beim Eintreffen bereits unterwegs sein. Ohne CORS-Freigabe des Headers kennt der Browser keine exakte Wartefrist.
- Eingabezeiten verwenden die lokale Browser-Zeitzone. Die Zielauswahl startet die Berechnung automatisch, standardmäßig ab aktuellem Standort und jetzt. Manuelle Start-/Zeitvorgaben bleiben erhalten. Routenanpassungen bleiben Entwürfe bis zur Übernahme und sind auch während Standortermittlung, Suche und Optimierung möglich. Die laufende Suche verändert keine offenen Eingaben; Abbrechen verwirft nur den Entwurf. Erst eine gültige neue Berechnung beendet die bisherige Suche. Gültige Einstellungsänderungen werden sofort gespeichert und lösen beim Verlassen eine neue Berechnung aus. Ungültige Zahlen bleiben mit einem Hinweis am Feld erhalten; „Fertig“, Tabs und Browser-Zurück innerhalb der PWA prüfen sie einheitlich. Bis zu einem neuen Ergebnis bleibt die bisherige Verbindung mit einem Hinweis auf die vorherigen Einstellungen sichtbar. Aktualisierung, Abbruch und neue Planung verhindern verspätete Antworten; fehlgeschlagene Aktualisierungen erhalten vorherige Ergebnisse.
- Die Vorschau zeigt den Stand ihrer Abfrage. Gestartete Navigation aktualisiert ÖPNV-Strecken im Vordergrund; eine Übergabe an die native App gibt es nicht.

## Zwischenziele und Planungslinks

„…“ im Routenkopf öffnet die weiteren Aktionen. „Planung teilen“ öffnet den Systemdialog zum Teilen der Planung. Ohne Unterstützung oder bei einem Fehler wird der Link kopiert; ist die Zwischenablage gesperrt, erscheint ein markierbares Linkfeld. Ein Abbruch des Teilen-Dialogs löst keine Kopieraktion aus.

Die [gemeinsamen Zwischenzielregeln](../documentation/bedienung.md#zwischenziele) gelten auch im Web; die PWA führt auch durch Zwischenstopps. Es werden nur vollständige Reisen durch alle Stopps angezeigt. Pausen gehören zur Gesamtzeit, das Radlimit gilt je Teilstrecke. Anfrage- und Zeitgrenzen beschreibt die [Routingdokumentation](../documentation/routing.md#planung-mit-zwischenzielen).

Neue Planungslinks verwenden `v=3` und enthalten nur Start, Ziel, Zeitpunkt sowie optionale geordnete Parameter `via1`, `via1Name`, `via1Stay` bis `via3`, `via3Name`, `via3Stay` (Koordinaten, Name, Aufenthalt in Minuten). Routing-Einstellungen werden nicht geteilt: Empfänger berechnen mit ihren eigenen Vorgaben. Bestehende Links mit `v=1` und `v=2` bleiben lesbar; ihre Routingwerte werden validiert, aber nicht übernommen. Ungültige oder unvollständige Stoppangaben verhindern die Berechnung. Browserhistorie, Kopieren und Offline-Snapshots behalten Stopps und Aufenthalte bei. Gespeicherte Ergebnisse behalten ihre ursprünglichen Berechnungswerte, ohne persönliche Vorgaben zu verändern.

## Vor öffentlicher Veröffentlichung

Der Build veröffentlicht nichts. Vor öffentlichem Start die erwartete Nutzung einschließlich zusätzlicher Routinganfragen mit Transitous abstimmen und Kontaktadresse prüfen. Die Nutzungsbedingungen erlauben nicht pauschal beliebige Routinglast. Referer, Datenquellen und Kartenattribution bleiben sichtbar bzw. aktiviert. Für größere Nutzung ist ein abgestimmtes Dienstangebot oder eigene Routinginfrastruktur erforderlich.

Die Website-Ausgabe liegt unter `docs/`. Für GitHub Pages kann nach separat beschlossener Veröffentlichung eine Branch-Quelle mit diesem Verzeichnis eingerichtet werden; Verfügbarkeit und Repository-Voraussetzungen anhand der [GitHub-Anleitung](https://docs.github.com/en/pages/getting-started-with-github-pages/configuring-a-publishing-source-for-your-github-pages-site) prüfen. Ein lokaler Build oder Vorschau-Server veröffentlicht keine Dateien.

Quellen:

## App-Oberfläche und PWA

- Mobil führt die Zielsuche zur bildschirmfüllenden Verbindungsliste. Jede Verbindung zeigt Abfahrt, Ankunft, Dauer, Verkehrsmittelkette und Aufwand. „Früheste Ankunft“ beziehungsweise „Späteste Abfahrt“ kennzeichnet die Empfehlung; Gelb markiert die Auswahl. Antippen einer Karte wählt die Verbindung aus und erhält die Listenposition. Nur „Details ›“ in der ausgewählten Karte öffnet den Reiseablauf mit lesbarer Etappen-Zeitleiste. Die Aktion hat in jeder Karte reservierten Platz, damit die Auswahl keine Kacheln verschiebt. „Alle Verbindungen“ und Browser-Zurück stellen Auswahl und Leseposition wieder her. Auch ein erneuter Tipp auf die ausgewählte Karte bleibt in der Liste. Es gibt keine Ziehgeste zum Vergrößern.
- Der offene Reiseablauf gruppiert Falten, Entfalten und Warten mit der folgenden Bewegungsetappe. ÖPNV-Etappen betonen Abfahrt und Linie und trennen Einstieg und Ausstieg mit den jeweiligen Gleisangaben. Bei Echtzeitverspätungen ab einer Minute bleibt die Planzeit sichtbar; darunter stehen die prognostizierte Zeit und beispielsweise „+15 min“ in Rot, getrennt für Abfahrt und Ankunft. Zwischenziele bleiben eigenständig, Zeitlücken ab einer Minute werden einmalig als Warten ergänzt. Bei Tageswechsel zwischen Reisebeginn, Reiseende oder verglichenen Zeiten tragen die betroffenen Zeiten ein Datum; gespeicherte Angaben behalten ihre Speicherkennzeichnung. Die optionale Planankunft wird auch ohne vollständige Fahrtreferenz gespeichert; ältere Reisen bleiben lesbar. Die Routenauswahl bleibt unverändert.
- „Karte“ öffnet mobil eine eigene Ansicht. „Alle Verbindungen“ führt zur Verbindungsliste; bei gespeicherten Strecken führt „Strecken“ zum Verlauf. Browser-Zurück folgt weiterhin der tatsächlichen Ansichtsfolge. Die kompakte Zusammenfassung verwendet dieselben Symbole, Zeiten und Aufwandsangaben wie die Verbindungsliste und bietet „Details“. Ein Routentipp auf der Karte wechselt nur die Auswahl. Kartenbewegung und Auswahl bleiben bei Ansichtswechseln erhalten. Verdeckte Kartenaktionen sind nicht per Tastatur erreichbar.
- Ab 900 px stehen Verbindungsliste und ausgewählter Reiseablauf in einer durchgehenden 420 px breiten linken Seitenleiste neben der Karte. Die Seitenleiste hat einen gemeinsamen Scrollbereich. Auswahlwechsel aktualisieren den Ablauf ohne Scrollsprung; „Details ›“ führt gezielt dorthin. Auf kleinen Bildschirmen oder bei großer Schrift darf die gesamte Routenansicht scrollen, damit alle Aktionen erreichbar bleiben.
- „Stand“ nennt den Abfragezeitpunkt. „Aktualisieren“ startet eine neue Suche und führt mobil zur Liste; bisherige Ergebnisse bleiben bis zum Ersatz mit einem Hinweis sichtbar. Fehler und Abbruch erhalten vorhandene Ergebnisse. Bei Planungsfehlern erscheint die passende Aktion direkt am Hinweis: „Erneut versuchen“ wiederholt den fehlgeschlagenen Auftrag, „Route anpassen“ öffnet ihn zum Bearbeiten. Offline-Zustand und bekannte Dienstsperrfristen deaktivieren Wiederholungen. „Neue Suche“ beendet die aktuelle Planung. Offline geöffnete Strecken zeigen ihren gespeicherten Reiseablauf mit Speicherhinweis; Zurück führt zum Verlauf oder zur Startseite. Unteransichten liegen in der Browserhistorie, nicht im geteilten Planungslink.
- „Alle Routen anzeigen“ unter der Standort-Schaltfläche passt alle angebotenen Alternativen einschließlich Fahrradvergleich und Zwischenstopps in die freie Kartenfläche ein; bei nur einer Verbindung heißt der Button „Gesamte Route anzeigen“. Die Aktion beendet eine laufende Standortabfrage und funktioniert auch offline; sie berechnet keine neue Route.
- Kartenmarker unterscheiden Start (dunkler Punkt mit weißem Ring), Ziel (gelbe Flagge) und Zwischenstopps (gelbe Nummern in Reisereihenfolge). Antippen oder Tastaturaktivierung öffnet Rolle und Ortsname. Identische Koordinaten teilen einen Marker mit allen Symbolen und Ortsangaben. Die Darstellung gilt auch für gespeicherte Offline-Reisen.
- Alternativen folgen wie iOS frühester Ankunft beziehungsweise spätester Abfahrt bei Ankunftsvorgabe. Links/Rechts-Tasten bewegen den Fokus zwischen Verbindungskarten; Enter wählt die Verbindung; „Details ›“ öffnet ihren Ablauf. Nachgeladene Ergebnisse werden automatisch ausgewählt, solange keine manuelle Auswahl erfolgte und keine Details bewusst geöffnet wurden. Ein Wechsel bleibt über die angezeigten Routenalternativen möglich.
- Die Ortssuche startet ab zwei Zeichen nach 280 Millisekunden Eingabepause und zeigt bis zu zwölf Transitous-Vorschläge. Die Detailzeile ergänzt den ersten benannten Stadtteil ab Verwaltungsstufe 9, sofern Transitous ihn liefert; doppelte Ortsangaben entfallen. Passende Favoriten zeigen die aktuellen Suchdetails und speichern sie bei Auswahl wie bisher, auch für die Offline-Anzeige. Alte Orte werden nicht im Hintergrund ergänzt. Vorhandene aktuelle Standortdaten gewichten die Suche regional; sonst dient München als Bezug, ohne andere Städte auszuschließen. Apple und Transitous können unterschiedliche Treffer liefern.
- Startseite sowie Start- und Zielauswahl zeigen Favoriten alphabetisch und bis zu fünf zuletzt verwendete Nicht-Favoriten. Bis zu 20 Nicht-Favoriten werden gespeichert. Auswahl zählt auch bei anschließenden Planungsfehlern; Favorisieren allein zählt nicht als Nutzung. Gleiche Namen innerhalb von 25 Metern werden zusammengeführt. „Aktueller Standort“ bleibt eine eigene Aktion und wird nicht favorisiert oder als fester Ort gespeichert.
- Stern, Ortsauswahl und ↖-Pfeil sind getrennte Aktionen. Der Pfeil übernimmt den Namen mit Leerzeichen und setzt den Cursor ans Ende; erst weitere Eingabe oder „Suchen“ lädt erneut. Favoriten und letzte Orte lassen sich auch offline ansehen. „Alle lokalen Daten löschen“ entfernt nach Bestätigung Orte, Einstellungen und den Streckenverlauf.
- Abfahrt und Ankunft stehen gleichwertig in der Kopfzeile. Nach Suchende erscheint ab 60 Minuten späterem Start ein Hinweis mit Zugang zu Einstellungen. Maßgeblich ist der ursprüngliche Anfragezeitpunkt; Ankunftssuchen und gespeicherte Reisen zeigen diesen Hinweis nicht.
- Antippen von Start/Ziel im Routenkopf öffnet „Route anpassen“ und bearbeitet Start, bis zu drei Zwischenziele, Ziel und Zeit als Entwurf. Zwischenziele lassen sich umordnen und mit 0–1440 Minuten Aufenthalt versehen. Beim Umkehren der Route kehrt sich ihre Reihenfolge mit um. „Aktuellen Standort verwenden“ fragt sofort den Standort und gegebenenfalls die Berechtigung ab. Nach Zielauswahl beziehungsweise beim bewussten Berechnen wird der Standort erneut ermittelt. Bei verweigertem Zugriff zeigt die App Hinweise zu Geräte- und Browsereinstellungen; eine gespeicherte Ablehnung kann sie nicht selbst zurücksetzen. Der separate Kartenknopf ändert nur den Kartenausschnitt.
- „Einstellungen“ speichert jede gültige Änderung. Die bisherige Verbindung bleibt als Ergebnis der vorherigen Einstellungen gekennzeichnet. Beim Verlassen über „Fertig“ oder einen anderen Tab wird einmal mit den letzten Werten neu berechnet; der gewählte Tab bleibt geöffnet. Browser-Zurück stellt den vorherigen Planungskontext wieder her. Browser-Vorwärts erhält einen noch ausstehenden Einstellungsversuch, ohne einen bereits abgeschlossenen Versuch automatisch zu wiederholen. Bei Fehlern bleibt die Verbindung verfügbar; „Erneut versuchen“ und „Route anpassen“ führen weiter. Alte Ergebnisse werden nicht unter den neuen Einstellungen gespeichert. Die Offline-Reise bleibt unabhängig davon als gespeicherter Stand erhalten.
- PWA-Build mit `vite-plugin-pwa` 1.3.0. Manifest und Service Worker liegen unter `plan/`, beide verwenden relative Pfade. Der Service Worker verwaltet nur diesen Bereich. Hashes innerhalb desselben Pfads benötigen keine Server-Rewrites.
- Nur lokale HTML-, JS-, CSS- und Icon-Ressourcen werden vorgeladen. Keine zusätzliche Speicherung oder Vorabdownloads von Transitous-Antworten und OSM-Kacheln. Die normale HTTP-Cache-Steuerung des Kartenanbieters bleibt bestehen.
- IndexedDB `foldroute-offline`, Version 2: Store `state` enthält `enabled`, den Verlauf `history` (Version 1) und den neuesten Snapshot `last`; Store `places` enthält Favoriten und letzte Orte. Reise-Snapshots ohne Zwischenziele verwenden Version 3, mit Zwischenzielen Version 4; Versionen 1 und 3 bleiben mit damaligen Einstellungen und unveränderten Zeiten lesbar. Speicheraktionen verwenden Transaktionen; Ausschalten leert `history`, löscht `last` und verhindert weitere automatische Reisespeicherung; Favoriten und letzte Orte bleiben erhalten. Ungültige gespeicherte Daten werden entfernt. Speicherfehler blockieren die Online-Planung nicht.
- Einstellungen liegen unter `foldroute.routing.v3` in `localStorage`. Der ältere Schlüssel `foldroute.routing.v1` wird nach erfolgreicher Migration entfernt.
- Der Tab „Strecken“ zeigt die letzten 20 unterschiedlichen Strecken, neueste zuerst. Es sind geplante Reisen, keine automatisch erkannten abgeschlossenen Strecken. Gleiche Start- und Zielorte mit denselben geordneten Zwischenzielen teilen einen Eintrag. Neue erfolgreiche Berechnungen ersetzen dessen gespeicherten Stand und rücken ihn nach oben. Abfragezeit, Einstellungen, Aufenthaltsdauer und gewählte Alternative unterscheiden keine Strecken. Ortsnamen werden unabhängig von Großschreibung innerhalb von 25 Metern verglichen; generische Standortnamen werden nur über die Nähe zugeordnet. Die Liste zeigt Start und Ziel in getrennten Zeilen, alle Zwischenziele in Reihenfolge als umbrechende „Über …“-Zeile und die letzte Planung mit relativer Tagesangabe. Mobil entfällt die sichtbare Seitenüberschrift. Wischen nach links legt „Löschen“ frei; die Geste selbst löscht nichts. Bei Mausbedienung bleibt die Strecke unverändert stehen; rechts ist Platz für einen 44-Pixel-Papierkorb reserviert, der bei Zeilen-Hover oder Tastaturfokus erscheint. Mit zusätzlichem Touchscreen bleibt er sichtbar. Die Wischgeste und ihre Demonstration gelten nur außerhalb des Mauslayouts. Eine einmalige Animation zeigt sie beim ersten nicht leeren Besuch auf Touchgeräten; reduzierte Bewegung und Nutzerinteraktionen unterbinden die Animation. Der Hinweisstatus liegt unter `foldroute.historySwipeSeen.v1` und wird beim vollständigen Löschen zurückgesetzt. Die letzte Löschung lässt sich acht Sekunden lang rückgängig machen (Pause bei Hover oder Fokus). Neuere Planungen, ein voller Verlauf und das Leeren oder Abschalten der Speicherung verhindern eine Wiederherstellung ohne bestehende Strecken zu verdrängen. Abfahrts- und Ankunftszeiten stehen in den gespeicherten Details. Stabile Eintragskennungen und separate Berechnungskennungen verhindern, dass verspätete Ergebnisse neuere Stände überschreiben.
- Antippen einer Strecke plant online direkt ab jetzt mit den aktuellen persönlichen Vorgaben: Start und Ziel bleiben fest, Zwischenziele und Aufenthalte werden übernommen. Die Verbindungsliste erscheint ohne Umweg über alte Ergebnisse. „Letzte Strecke erneut planen“ auf der Startseite verwendet denselben Ablauf. Ohne Internet öffnet sich die gespeicherte Kopie mit gekennzeichnetem Abfragezeitpunkt. „Jetzt neu planen“ ist dort direkt sichtbar und offline deaktiviert; „Mit gespeicherter Route starten“ bleibt im Menü erreichbar. Browser-Zurück und Vorwärts stellen Ergebnisse wieder her, ohne erneut zu suchen.
- „Strecken auf diesem Gerät speichern“ ist standardmäßig eingeschaltet. Ausschalten löscht den Verlauf; einzelne Strecken lassen sich im Tab löschen, der gesamte Verlauf nach Bestätigung in den Einstellungen. Die vorhandene Einzelreise wird beim ersten Zugriff einmalig übernommen. Der versionierte Verlauf liegt unter `state.history` in der bestehenden IndexedDB-Datenbank; `state.last` bleibt als neuester Snapshot erhalten. Vorhandene Streckenduplikate werden beim Lesen zusammengeführt und atomar gespeichert; der neueste gültige Stand bleibt erhalten. Beschädigte Einträge werden einzeln entfernt. Parallele Schreibvorgänge begrenzen den Verlauf atomar auf 20 Einträge.
- Offline-Neustart öffnet die letzte Reise als gespeicherten Stand. Die Kartenfläche zeigt nur die gespeicherte Geometrie auf neutralem Hintergrund. Zeiten werden nicht als aktuelle Echtzeitdaten dargestellt. Ohne gespeicherte Reise bleibt ein erklärter Leerzustand. Netzrückkehr startet keine Berechnung.
- Updates zeigen „Neue Version verfügbar“. Erst „Aktualisieren“ aktiviert den wartenden Service Worker und lädt neu. Während einer Berechnung, eines Anpassungsdialogs oder aktiver Navigation ist die Updateaktion gesperrt. „Später“ erhält die laufende Ansicht.
- Die Icons wurden aus `public/app-icon.svg` mit dem PWA Assets Generator 1.0.2 erzeugt (Preset `minimal`, `resizeOptions.background: '#171A1C'` für `maskable` und `apple`). Der Generator war nur für diesen einmaligen Exportschritt installiert; die PNGs und das SVG liegen im Repository.

Installation funktioniert auf HTTPS oder lokal auf `localhost`/`127.0.0.1`. Ein HTTP-Link mit einer LAN-IP reicht für eine vollständige PWA-Prüfung auf dem iPhone nicht aus. In Safari über Teilen → „Zum Home-Bildschirm“ installieren; falls angeboten, „Als Web-App öffnen“ aktivieren. Die Einstellungen zeigen diese Anleitung beziehungsweise den unterstützten Browser-Installationsdialog. Ein Browser kann gespeicherte Daten wieder entfernen; Offline-Verfügbarkeit setzt einen zuvor erfolgreichen Online-Aufruf voraus.

Vor Veröffentlichung auf einem echten iPhone prüfen: Installation und Icon, eigenständiges Fenster, Safe Areas, Tastatur bei Ortssuche und Anpassung, Offline-Neustart sowie Updateübernahme. Automatisierte Chromium- und WebKit-Tests decken diese Geräteeigenschaften nicht vollständig ab.

Die Kartenübersicht bleibt beim Wechsel zwischen Alternativen stehen. Nachgeladene Umwege erweitern sie bei Bedarf; entfallene Alternativen verkleinern sie nicht automatisch. Eigenes Verschieben oder Zoomen pausiert automatische Anpassungen bis zur Übersichtsaktion oder einer neuen erfolgreichen Berechnung. Auch der eingeblendete Fahrradvergleich gehört zur gemeinsamen Übersicht.

### Live-Standort auf der Routenkarte

Bei vorhandener Standortfreigabe aktualisiert die sichtbare Routenkarte im Vordergrund einen separaten blauen Standortpunkt. Der transparente Kreis zeigt den gemeldeten Genauigkeitsradius in Metern. Über 100 Meter gilt die Messung als ungenau; nach 60 Sekunden ohne frische Messung oder bei einem Ortungsfehler erscheint der letzte Punkt grau. Der geplante Start bleibt fest. Standortupdates verändern weder Route noch Kartenausschnitt; der Standortbutton zentriert einmalig.

Beim Wechsel zur mobilen Liste oder zum Reiseablauf, zu Einstellungen/Strecken, Öffnen der Routenbearbeitung und Verlassen der App pausiert die Ortung. Ohne Freigabe wird sie erst durch eine ausdrückliche Standortaktion angefragt. Unterstützt der Browser keine Berechtigungsabfrage, ist auch nach Rückkehr eine solche Aktion nötig. Die Position bleibt ausschließlich im Arbeitsspeicher; es entsteht keine GPS-Spur und keine zusätzliche Routinganfrage. Während aktiver Navigation verarbeitet die Standortüberwachung zusätzlich den Fortschritt und erkannte Routenabweichungen.

Die lokale Einstellung „Bildschirm während der Route eingeschaltet lassen“ ist standardmäßig aktiv. Die PWA fordert einen Screen Wake Lock für sichtbare Verbindungsliste, Reiseablauf, Karte und aktive Navigation an und gibt ihn bei Routenbearbeitung, Ansichtswechsel oder Hintergrundwechsel frei. Bei Rückkehr wird er erneut angefordert. Fehlende Unterstützung oder eine Ablehnung durch das System beeinträchtigen die Planung nicht. Die Einstellung wird nicht in Planungslinks oder Routing-Einstellungen übernommen.

### Adressen im Streckenverlauf

Generische Start- und Zielnamen werden nach dem Speichern und beim Öffnen des Verlaufs asynchron über Transitous (`/api/v1/reverse-geocode`) ergänzt: Straße, Hausnummer und Ort. Fehlt eine nahe Adresse (maximal 100 Meter), erscheint Stadtteil/Ort. Bewusst ausgewählte Namen bleiben erhalten. Gespeicherte Koordinaten, Routen und Zeitstempel ändern sich nicht; es gibt keine neue GPS- oder Routingabfrage. Erkannte Namen bleiben offline verfügbar. Anfragen laufen einzeln, mit zehn Sekunden Timeout; erfolglose Anfragen werden frühestens nach fünf Minuten bei einem weiteren Verlaufsbesuch erneut versucht. Hintergrundwechsel bricht offene Ergänzungen ab. Löschen verhindert verspätete Schreibzugriffe.

## Navigation in der PWA

Feste Abfahrts- und Ankunftszeiten dürfen auch in der Vergangenheit liegen. Zeitwahl, Planungslinks, Aktualisieren und Wiederholen behalten den gewählten Zeitpunkt bei, auch mit Zwischenzielen. Die Verfügbarkeit historischer Fahrplandaten hängt vom Routingdienst ab. Ein vergangener Suchzeitpunkt sperrt die Suche oder den Navigationsstart nicht allein; „Los“ bewertet die konkrete Verbindung.

„Jetzt“ in der Zeitwahl trägt einmalig das aktuelle lokale Datum und die aktuelle Minute ohne Aufrunden oder Vorlauf ein. Abfahrt beziehungsweise Ankunft bleibt ausgewählt. Die Werte laufen nicht mit und bleiben auch bei Hintergrundwechsel und Mitternacht stehen; erneutes Antippen aktualisiert sie. „Übernehmen“ speichert genau die angezeigten Werte als festen Zeitpunkt, Abbrechen verwirft den Entwurf. Die schnelle Zielsuche ohne bestätigte Zeitwahl, `timing=now`-Links, „Ab jetzt suchen“ und das erneute Planen gespeicherter Strecken verwenden weiterhin den aktuellen Zeitpunkt nach der Standortermittlung.

Beim Bearbeiten nach einer Suche übernimmt „Route anpassen“ den ursprünglichen Suchzeitpunkt minutengenau als feste Abfahrt; eine feste Ankunft bleibt unverändert. Maßgeblich ist die Suchvorgabe, nicht die Abfahrt einer vorgeschlagenen Verbindung. Eine laufende oder fehlgeschlagene neue Anfrage hat Vorrang vor älteren Ergebnissen. Solange deren Standort und Suchzeitpunkt noch nicht aufgelöst sind, bleibt der Entwurf bei „Jetzt“. Suchupdates verändern einen bereits geöffneten Entwurf nicht. Erst „Route berechnen“ bestätigt die feste Zeit, auch wenn nur Orte oder Zwischenziele geändert wurden. Abbrechen lässt die ursprüngliche Suche und ihr Aktualisierungsverhalten unverändert.

„Los“ in der festen Startleiste startet die ausgewählte Reise. Daneben steht die Ankunft hervorgehoben, darunter die Dauer. Start/Ziel im Kopf öffnet die Routenbearbeitung; „…“ enthält Teilen, Aktualisieren und bei gespeicherten Reisen „Jetzt neu planen“. Die ausgewählte Route wird durch einen gelben Rahmen statt einer vollständig gelben Fläche markiert. Standortdaten dürfen höchstens 60 Sekunden alt und auf höchstens 100 Meter genau sein. Die Startprüfung bleibt in der Ergebnisansicht und erhält die Auswahl. Unter 250 Metern zum Start oder auf der ersten Bewegungsetappe beginnt die Reise direkt. Bis 25 Kilometer kann eine Rad-Anfahrt vorgeschaltet werden; gewählte ÖPNV-Fahrten bleiben erhalten. Darüber bietet die App „Ab hier suchen“ an. „Anschluss gefährdet“ warnt anhand verbleibender Wege, Faltzeit und vorhandener Einstiegspuffer; es gibt keine zusätzliche feste Zeittoleranz und zukünftige Abfahrten bleiben startbar. Die Startleiste bleibt auch während der Suche sichtbar. Ohne Ergebnis, während der Startprüfung oder bei gesperrtem Start ist „Los“ deaktiviert; während der Optimierung bleibt eine startbare Auswahl nutzbar. Bei einer laut aktuellen Daten zurückliegenden Abfahrt oder einem Ausfall zeigt die Leiste den konkreten Grund und „Ab jetzt suchen“. Bei Startfehlern bietet sie die passende Wiederholung; die Verbindungsdetails bleiben über „Details“ erreichbar. Fehlende aktuelle Fahrtdaten werden als unklare Erreichbarkeit angezeigt. Die gewünschte Ankunftszeit bleibt bis zur ausdrücklichen Änderung erhalten; aktualisierte Ankunftsprognosen können davon abweichen.

Die Navigationsansicht zeigt Abbiegehinweise, Entfernung, aktuelle Etappe und Ankunft. OpenLayers 10.11.0 dreht die zweidimensionale Karte in Fahrtrichtung; die Vorschau verwendet weiter Leaflet. GPS-Richtung wird ab 1 m/s verwendet, im Stand bleibt die letzte Richtung erhalten. Verschieben, Zoomen und Drehen pausieren die Kamera; „Standort folgen“ zentriert erneut. Alte gespeicherte Straßenetappen ohne Manöver bleiben als Streckenverlauf nutzbar und kennzeichnen fehlende Abbiegehinweise.

„Navigation beenden“ führt ohne neue Routensuche zum Reiseablauf der verwendeten Verbindung zurück. „Los“ startet sie nach der normalen Standort- und Fahrtdatenprüfung erneut. Auswahl, aktualisierte Fahrtdaten und ursprünglicher Abfrage- beziehungsweise Speicherzeitpunkt bleiben erhalten. Passende Alternativen bleiben verfügbar; nach einer übernommenen Neuplanung oder geänderten Routingvorgaben wird nur die aktuelle Verbindung angezeigt. Das Beenden erzeugt keine Archivkennzeichnung und keinen neuen Abfragezeitpunkt. Ortung und Sprachführung der Navigation sowie der gespeicherte Wiederaufnahmezustand werden beendet; eine neue Navigation übernimmt keinen alten Fortschritt. Direkt geöffnete Archivkopien behalten ihren Speicherhinweis und ihre bisherigen Aktionen.

Auf schmalen Displays steht die Fahranweisung oben und eine kompakte Leiste mit Restdauer, Ankunft und Beenden unten. Antippen oder Hochziehen öffnet Etappen, Echtzeitstatus und manuelle Abschnittsbestätigung; Herunterziehen schließt die Details. Warnungen bleiben kompakt sichtbar, „Verbindung ansehen“ öffnet einen Alternativvorschlag. Erfolgreiches Übernehmen schließt die Details. „Weiterfahren“ an Zwischenstopps bleibt direkt erreichbar.

Bei fehlendem oder veraltetem Standort steht unter dem oberen Navigationsbereich „Kein GPS“, bei ungenauer Position „GPS ungenau“. Der kleine Statushinweis bleibt bis zu einem gültigen Standort sichtbar; der Positionspfeil wird währenddessen grau und der automatische Fortschritt pausiert. Erklärung und „Standort erneut anfragen“ stehen zusammen in den Reisedetails. Ein Timeout fordert keine Änderung der Standortberechtigung; Hinweise dazu erscheinen nur bei verweigertem Zugriff. Gültiger GPS-Empfang entfernt Standortfehler automatisch, ohne andere Navigationsmeldungen zu löschen.

Rad- und Fußetappen werden entlang ihrer Geometrie verfolgt. Drei genaue Positionsmeldungen mit mehr als 60 Metern Routenabstand lösen eine Neuberechnung aus; höchstens einmal je 30 Sekunden. Bei verbleibenden ÖPNV-Etappen wird die neue Reise erst mit „Verbindung übernehmen“ aktiviert; das gilt auch für notwendige Neuplanungen nach Zwischenstopps. Reine Rad-/Fußrouten dürfen weiter automatisch angepasst werden. Fehler und abgelehnte Vorschläge erhalten die bisherige Route und den Fortschritt. Zwischenstopps warten auf „Weiterfahren“ und erhalten ihre geplante Aufenthaltszeit; nur verbleibende Stopps gehören zur Neuplanung.

Aktuelle und verbleibende ÖPNV-Strecken werden über `/api/v6/trip` beim Start und etwa alle 60 Sekunden aktualisiert. Die Anzeige unterscheidet Echtzeit, Fahrplan, veraltete und fehlende Daten. Nach 120 Sekunden gelten Daten als veraltet; fehlerhafte Abrufe warten zwei, vier, anschließend fünf Minuten. Längeres `Retry-After` gilt für alle weiteren Fahrtabrufe. Strecken ohne eindeutige Referenz bleiben verfügbar, erlauben aber keine automatische zeitbasierte Fortsetzung in oder aus unzuverlässigem ÖPNV. „Abschnitt fertig“ beziehungsweise „Ausgestiegen“ ermöglicht eine bewusste Bestätigung.

Ausfälle und gefährdete Anschlüsse führen zu einem Alternativvorschlag, den du übernehmen oder ablehnen kannst. Im Zug beginnt die Alternative am vorgesehenen Ausstieg. Bei ausgefallenem aktuellem Halt erst den tatsächlichen Ausstieg vor Ort prüfen und bestätigen. Sprachansagen sind standardmäßig eingeschaltet und über „Ton an“ stummschaltbar; ihre Verfügbarkeit hängt von Browser und installierten Stimmen ab. Die Toneinstellung verändert keine Routing-Einstellungen.

Navigation funktioniert bei geöffneter, sichtbarer PWA. Bildschirm-Wachhalten folgt der vorhandenen Einstellung. Bei App-Wechsel werden Ortung, Berechnungen und Sprache pausiert; nach Rückkehr benötigt automatischer Fortschritt wieder einen aktuellen Standort. Kein Hintergrund-GPS, keine Push-Navigation und keine Offline-Karten. Ohne Netz bleiben gespeicherte Geometrie und Hinweise verfügbar, sofern Oberfläche und Navigationsmodule bereits offline bereitstehen. Sprachausgabe kann je nach Gerätestimme Internet benötigen.

IndexedDB `state.activeNavigation` enthält einen versionierten Zustand mit Reise, Einstellungen, Abschnitt, Manöver, Streckenfortschritt und bestätigten Stopps. Koordinaten der gemessenen GPS-Positionen werden nicht gespeichert. Neuladen oder erneutes Öffnen bietet „Navigation fortsetzen“ und „Verwerfen“; es startet keine Ortung ohne Bestätigung. Vergangene zeitgesteuerte Abschnitte müssen nach Wiederaufnahme bestätigt werden. Beenden oder Ankunft löscht den Zustand. „Strecken speichern“ gilt auch für Wiederaufnahme; Ausschalten löscht beide Speicherarten. Speicherfehler unterbrechen die laufende Navigation nicht.

Tests: `npm test`, `npm run test:parity`, `npm run build`, `npm run test:browser`. Navigationsfälle laufen mit simuliertem GPS und abgefangenen ÖPNV-Anfragen in Chromium und WebKit. Vor Veröffentlichung weiterhin echte installierte iPhone- und Android-PWAs bei Bewegung, Bildschirmwechseln und Sprachausgabe prüfen.
## Adressen über das Teilen-Menü übernehmen

Die mit Chrome auf Android installierte PWA kann als **FoldRoute** im Teilen-Menü erscheinen. Nach einem Manifest-Update muss Chrome die installierte App aktualisieren; bei ausbleibendem Eintrag die Installation erneuern. Adressen und direkt auswertbare Apple-/Google-Maps-Links werden als neues Ziel übernommen. Eindeutige Ziele starten eine Suche ab aktuellem Standort für **Jetzt** mit den eigenen Einstellungen; mehrere Treffer öffnen die Ortsauswahl. Eine gespeicherte aktive Navigation wird vor einer neuen Suche ausdrücklich abgefragt.

Reine Karten-Kurzlinks werden nicht abgerufen oder über einen zusätzlichen Dienst aufgelöst. Stattdessen lässt sich eine Adresse eingeben. Ein abgebrochener Import bleibt über **Geteiltes Ziel** erreichbar; ein neuer Import ersetzt den vorherigen. Vorgemerkte Ziele bleiben lokal und werden mit **Alle lokalen Daten löschen** entfernt. Ohne verfügbaren lokalen Speicher funktioniert die Übernahme für die laufende Sitzung.

Unter iOS kann die PWA selbst kein Teilen-Ziel registrieren. Dafür gibt es die native [iOS-Teilen-Erweiterung](../ios/README.md#adressen-aus-anderen-apps-übernehmen). Keine Kurzbefehle erforderlich.
